## Follow-up analysis (unattended block, 06:40 UTC)
- **ENDP.AFS128;1 is not a bug.** The `128` typo is in game data (already recorded in docs/MOVIE_FINDINGS.md); real hardware also fails that probe. The four `vfprintf error` lines are the game's own debug strings "DVCI: \"%s\" found/Not found / Total %d files / Warning, Can't load all cache file" (formats 0x35b338-0x35b380) printed to a stdio handle the runtime does not model; harmless. Earlier note above that blamed the name normaliser was wrong.
- **Fast-VU1 A/B mismatch is a timing-hazard artefact, not a logic bug.** The fast path (ps2_vu1_core.cpp runFast) applies MAC/STATUS/CLIP, Q, P and stores immediately and advances one cycle per instruction pair without register-ready stalls, so cycle counts differ (378 vs 423) and a program that reads a flag register inside the hardware latency window sees the post-write value in fast mode and the stale one in exact mode. In all four mismatching programs the first differing byte is the same: low 16 bits of word 0 of the qword at GIF offset 208 (0x0FF0 exact vs 0x8FF0 fast): bit 15 = the MAC sign-x flag leaking into an otherwise denormal float lane (value ~1e-41), which the GS treats as 0 either way. Conclusion: no rendering impact; a faithful fix would need the full flag pipeline with stall modelling (i.e. use the exact path), so nothing was changed. If A/B noise is unwanted, mask denormal-only differences in the checker.
