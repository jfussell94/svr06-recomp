# Hang at "NOW LOADING" before the demo (user-reported 02:21 local, build with MMI/flag/FPU-switch patches)
Evidence (analysis/run_err.txt, run_out.txt, shots/shot_39.png):
- Title ("Press START") reached; idle timeout starts the demo load; screen stays on the Shawn Michaels "NOW LOADING..." picture for 10+ minutes. Process alive, no crash, no exception, no missing-target/JALR/Dormant lines, no [canary], no heap NULL in the last allocations.
- Main thread (th1) keeps cycling the frame callback (loops counter 0x2DA3 and rising), GS/VU0 keep drawing, so this is a stuck loading *state*, not a dead process.
- The `[sema] spin` lines are idle worker threads (th3 entry 0x1C0980 job-queue thread, th5 0x113C80, th2 0x2D7490) waiting on empty queues; they are not the cause.
- Last distinct activity before the stall: big alloc `memalign 0x160980` (ra 0x1C7CD0 -> 0x01535600), then sound-driver RPCs to sid 0x301 fn 0x67/0x6C/0x68 from worker th3 (callback 0x1C0A20), with IOP SPU DMA writes (irq 0x28, 0x24). No further CD reads or `[resload]` after that, i.e. the load never reaches the motion/PAC match-data stage (the 14 MB `memalign 0xD60000` of ISS-100 never happens in this run).
- IOP thread id=17 (entry 0x4E780, prio 39) ends in state 5 (dormant) with waitId=12 from ~6.1 G IOP cycles on.
- The sound-driver upload (SPU) is therefore the prime suspect: the game waits for a sound-bank/SPU completion that the IOP-side emulation does not deliver.
Not caused by (by inspection): flag patches (clip/overlap code only), PMULTH/PHMADH patches (pixel blend + matrix dot), FPU switch (off). Needs a bisect to be sure; the earlier 06:07 run only visited menus, so demo load was last known-good on the 10-27 build (arena rendered, then ISS-100 freeze).
Next steps (no run needed first): trace what sid 0x301 fn 0x67/0x6C/0x68 expect back (reply buffer / completion flag) and which flag the main load state polls; check the IOP thread 17 exit reason; then bisect by rebuilding with the .bak patches reverted only if the sound path is cleared.

(Correction 05:30: fn 0x69 appears in the plain-read build too, only later in the run; it is not an artefact of the live read-backs.)
- Exact stall point: the whole sound bank is uploaded (SPU DMA core1 0x5010, 0x25010 ... 0x145010 in 0x20000 steps, last 0x980 bytes to 0x165010 = about 1.4 MB, from SOUND.PAC lsn 0x120263, 0x14EA800 bytes). After the last DMA completion interrupt (irq 0x28 -> handler 0x220EC, sema 8 signal) nothing further happens: no CD read, no resload, no sound RPC. IOP thread 17 (entry 0x4E780, prio 39) sits at pc 0x4E7C0 waiting on IOP semaphore 12; IOP thread 11 (entry 0x49288) is just a 1-second heartbeat loop; EE worker threads th2/th3/th5 wait on empty queues; EE main thread th1 waits flag mainWaitFlag=1 (ra 0x14CBD8) and keeps running the frame callback.
- The game's SPU2 programming never enables the SPU interrupt (CORE_ATTR values 0xC000/0xC001/0xC080/0xC081/0xC0A1: IRQ-enable bit 6 clear, IRQA 0x19C/0x19E never written), so a missing SPU IRQ is NOT the missing event. Candidates now: (1) semaphore 12 is signalled by a timer/alarm or by the DMA-complete path we deliver too early/late; (2) the EE side expects the reply of the pending sound RPC (fn 0x67) to arrive after the IOP finished the bank upload (our RPC completes synchronously before the DMA); (3) a SIF register/flag the IOP driver sets at the end of the bank load.

## Update 05:40 - what fn 0x69 is, and the real slowdown
- fn 0x69 (2368-byte request, `[snd69]` dump) is a voice/stream packet submission: +1c = own address (alternating buffers 0x203D69C0 / 0x203D7300), +24=1, +28/+2c/+30 sizes (0x1000 / 0xF5C...), +38 first sample words, +44 = running packet sequence (1,2,3,...), +920=1. The EE sends one per loader pass; the IOP echoes the buffer back.
- The game's IOP->EE completion messages (`[iop-rpc] CallRpc(IOP->EE) fn=1 -> [ee-rpc-srv] queued sid=0x200 fn=1 func=0x1C0D60`) deliver the EE callback pointer stored at +0x14 of the message; the handler 0x1C0D60 calls it via 0x1C0C60.
- ROOT OF THE SLOWNESS: `g_svr06Flags` defaulted to 1024 (SvrConsole.cpp), i.e. every VU1 program was run twice (fast + exact) and compared (`[vuab]` lines, vuprof ready=124 cyc/pair). That made vu1run ~5 s of work per 3 s of wall time and the loading screen run at 2-10 fps, so the loader (one step per frame) crawled for 10+ minutes. Fix: default is now 0 (fast VU1 only); SVR06_VUAB=1 re-enables the A/B check (changelog CL-0040 area). Verify: load time and `[tprof] vu1run` should drop to well under the 3 s window.
