## CL-0053 [v0.4.0] — Vulkan (paraLLEl-GS) now renders the game picture
- Root cause of the black Vulkan output: HLE libgs/kernel stubs write GS registers (FRAME_1/2, ZBUF, etc.) directly via `GS::writeRegister`, bypassing the GIF stream, so paraLLEl-GS never saw them (FRAME was 0 → nothing drawn).
- Fix: `GS::writeRegister` forwards to `gsvk::writeReg` (A+D GIF packet on PATH3) when `SVR06_GS=vulkan`.
- GIF path ids mapped to paraLLEl-GS indices (PATH1→0, PATH2→1, PATH3→2); image uploads use index 2; counters print all four.
- Granite thread index registered (silences "Thread does not exist in thread manager" log spam).
- Added `[gsvk] regs` diagnostics and env `SVR06_VKSELFTEST=1` (draws a red sprite to verify scanout/readback).
- Verified: PPM dump shows in-match demo frame (512x512 scanout) rendered by Vulkan on AMD RX 6700.

## CL-0059 [v0.4.0] — Vulkan: DISPLAY register convention fix (screens drawn 1/4 width)
- Symptom (user screenshot 21:47): memory-card CAUTION screen squeezed into the top-left ~160 px; same for the legal screen (text only in the left quarter of the 2560-wide scanout).
- Cause: those screens' DISPLAY1 arrive in the runtime's pixel convention (DW = width-1 = 639, MAGH = 0, DH = 255), but paraLLEl-GS/real GS use dot-clock units (DW = 2559, MAGH = 3 for 640 px, MAGH = 4 for 512 px). Real-convention values (e.g. 0x1fd9ff0204e27c: MAGH 4, DW 2559) were already fine.
- Fix (`gs_vulkan_bridge.cpp`, backup `.bak_display`): `fixDisplay()` converts MAGH==0 && 63<=DW<2559 to mag = 2560/(DW+1), DW = (DW+1)*mag-1; logs `[gsvk] DISPLAY convention fix: old -> new` on change. Applies to DISPLAY1/2.
- Also this build: CL-0058 speed-ups measured: title 55 FPS green, memory-card screen 50 FPS (was 29 with black-frame rescans, 48 before the readback changes).
- NOT yet verified visually; check the caution and legal screens after rebuild. Next CL number: CL-0060.

### CL-0127 - ISS-144 async VIF1/GIF worker thread (opt-in, debug flag 15) (2026-11-05)
Design after hctp-recomp's ChainWorker (GPL-3.0, credited; see Project doc claude/hctp-vu1-speed-research-2026-11-05.md). With debug flag 15 (value 32768, live toggle `svrlive.py flag 15 1`):
- At a GIF or VIF1 DMA kick the game thread copies the transfer bytes (chain mode already did; normal mode now copied too) and completes the DMA exactly as before (D_STAT, CHCR, MADR/QWC, DMA-end handlers unchanged). A worker thread then runs GIF path 3 submits, VIF1 processing (incl. all VU1 runs and XGKICKs) and the GIF arbiter drain, in kick order. VIF0 stays on the game thread.
- The game thread waits for the worker (fence) only when it touches worker-owned state: GS privileged registers (any read/write, via isGsPrivReg), GIF/VIF register reads/writes 0x10003000-0x10003FFF, the VIF1 FIFO, EE access to VU1 code/data memory (mapVuMemory), VIF1 to-memory readback (DIR=0), any synchronous processPendingTransfers, GS stubs (GS.cpp clears/readbacks, Font.cpp), the runtime's native GIF chain fast paths.
- Stats line `[vifasync] 3s: jobs=N fences=M`.
Files: ps2_memory.cpp, ps2_runtime.cpp, Kernel/Stubs/GS.cpp, Kernel/Stubs/Font.cpp (backups .bak_vifasync). Flag off = previous synchronous behaviour (only an idle atomic check per fence point).
Known risks to watch: flicker if the game flips display buffers without a GS sync; a deadlock if a non-game thread fences while the worker waits on it; diagnostics statics now touched from the worker.

## CL-0133 (2026-11-06) VU1 fast path: ~26% fewer instructions, bit-identical (offline-verified)
- New offline harness (no game): the VU1 interpreter sources compile natively on Linux with a small bench (`bench.cpp`: the 10 hot entrance programs from the PCSX2 capture; hashes of all registers, flags, VU data and every GIF packet) and a differential fuzzer (`fuzz.cpp`: 4000 random programs incl. flags/DIV/branches/XGKICK, original vs new build, modes 0 and 512). Profiled with callgrind.
- Changes (all produce identical hashes in every bench program and all 4000 fuzz programs, fast and exact modes):
  - execUpper: inline Q/I operand normalisation; broadcast reads the already-normalised lane; SSE fast path for ADD/SUB/MADD/MSUB/MUL (bc/vector/Q/I, VF and ACC forms) with the same lane-wise IEEE operations.
  - FMAC result store: table-driven normalise + flags blended straight into the destination (ps2_vu1_fmac_fast.h fmacFinish), inlined with the flag push (new ps2_vu1_inline.h).
  - Flag pipeline: valid-slot bitmask + push-order FIFO (ready entries are a FIFO prefix, applied in slot order exactly as before); inline flags-only commit in the run loop.
  - Run loop: per-pair facts precomputed at decode (reserved, D/T/E bits, FDIV/WAITQ, branch-delay VI); the halt/end chain is skipped when it cannot fire.
- Callgrind: 1,458M -> 1,082M instructions for the bench (-26%). Expected in game: VU1 time per 3 s from ~2.0 s to ~1.5 s.
- Backups: ps2_vu1.h / ps2_vu1_core.cpp / ps2_vu1_upper.cpp / ps2_vu1_fmac_fast.h `.bak_cl0133`.
- CL-0133 second batch (same day): decoder now stores pre-decoded fast forms per pair (FMAC arithmetic: op/source/dest/regs; lower LQ/SQ/LQI/SQI/MOVE/IADDIU/ISUBIU/IADD/ISUB/IADDI/IAND/IOR) and the run loop executes them inline (forced inline helpers in ps2_vu1_inline.h); other ops still use execUpper/execLower. Callgrind 1,458M -> 931M (-36%); wall time on the bench ~1.5x faster. Still bit-identical: bench hashes in modes 0/512/65536 and 4000 fuzz programs in modes 0/512.
- CL-0133 third batch: inline commit now also handles the FDIV (Q) result (the fast path only ever has flags/FDIV pending); pre-decoded ITOF0/4/12/15, FTOI0/4/12/15, ABS, MAX/MINI (bc/vector/I). - CL-0133 fourth batch: inline B/BAL/IBxx; fast-path XGKICK copies each GIF tag's data in one memcpy instead of one qword per call (the fast path completes the XGKICK inside startXgkick anyway; same bytes, totalBytes and failure checks). Bit-identical in bench + fuzz.
